### Failure-suite defects found and fixed (none were product defects)

Four runs on 2026-09-12. Every check has now passed at least once on a real injected fault, and no product defect
has appeared in any of them. The remaining work is one clean pass of the whole suite with all fixes applied.
Each check can now be re-run on its own: `run_failure_suite.sh <check> [...]`, names from `-l`.

| Defect | Root cause | Fix |
|---|---|---|
| `compose_restart` reported no alert after the restart, though 414/414 records were delivered and stored | The suite replayed the same `scan` against the same entity three times in four minutes. `incidents.py` suppresses a repeat finding inside an open incident (`incident_idle_ms` = 300 s) when severity, subtype and evidence have not grown - the documented, wanted behaviour. The identical scan 7 minutes later passed, once the incident had idle-resolved | Each fault now replays a different scenario (`scan`, `dga`, `udp_amplification`, `dns_tunnel`, `syn_flood`) |
| `archive_lifecycle` first run: the injected archive outage never happened | `docker compose run --rm archive-exporter` starts the service's dependencies, and it declares `depends_on: minio-init`, so the harness restarted the MinIO it had just stopped | `run --rm --no-deps` |
| `archive_lifecycle` second run: nothing exported even with MinIO back | The previous run left this partition's manifest row at status `deleted_hot`, which is neither `None` nor `stale`, so the exporter correctly skipped the partition | The test purges its own manifest row before inserting the aged rows |
| `link_injection` second run: 0 of 15 bad frames quarantined | `inject.py` derived its boot id deterministically from the case name and used fixed sequence numbers, so a second run replayed identical (sensor, boot, sequence) triples and the receiver's persisted dedup window suppressed them as duplicates before validation - again correct behaviour, wrong test | The injector now uses a fresh boot id per invocation |
| `clickhouse_outage` second run: no new notifications observed | The check slept a fixed 90 s after the replay. `syn_flood` is a much heavier capture than the `scan` it replaced, so the window closed before the alert arrived. The notifier has no ClickHouse dependency at all (`notifier.py` writes only to SQLite), so this was never an outage-tolerance failure | Polls for a new notification for up to 300 s with ClickHouse still stopped |
| `link_injection` on every re-run: 0 of 15 frames quarantined | `inject.py` derived its boot id from the case name and used fixed sequence numbers, so a re-run replayed identical (sensor, boot, sequence) triples and the receiver's persisted dedup window suppressed them as duplicates before validation | Fresh boot id per invocation. Confirmed: gaps rose by exactly 34464 again and `link_duplicate_records_total` stayed flat |
| The injector fix appeared to do nothing | Code under `ingest/`, `consumers/`, `flink/`, `tests/e2e/` and `data-generator/` is baked into the images, not mounted, so the container kept running the old `inject.py`. `git pull` alone changes nothing | `docker compose build` before re-running; the script header now says so |
| `link_injection` after the rebuild: 14 quarantined, assertion wanted 15 | `invalid_id` is deterministic in (reason, payload sha256, sensor, boot, sequence) and `invalid_events` replaces on it. The `malformed` case sends fixed bytes with no frame identity, so its 3 copies collapse to 1 row - and that row already exists from the first ever run, contributing 0 new rows. 14 is the correct steady-state count (3+3+3 plus 3 schema violations and 2 gap frames that are also schema violations); 15 only held on a virgin stack. The dedup is a wanted replay-safety property | Assert per reason code with explicit expected counts instead of a magic total |
| `jobmanager_restart` and `clickhouse_outage` in run 3 | Not reproducible after the rebuild: both passed in run 4 on the same faults. The dga miss was not lag (264/264 stored, 40 alert updates tagged to that run) and not detector-state carryover (the DGA burst window clears its domain map per window) - most likely the stale `tests/e2e` and detector code in the pre-rebuild images | Covered by rebuilding before a run; both checks pass |
| `taskmanager_kill` asserted the same job id after the kill | The TaskManager is absent ~25-30 s (sleep plus `up -d`), long enough that the job can lose its slots and the supervisor resubmits it from the newest retained checkpoint before Flink's own `exponential-delay` restart wins. Both are correct recovery; which one happens is a race, so the check passed or failed on timing | Accept either path, record which one occurred, and still require post-fault detection |

The suite is not idempotent against a live stack: re-running it within 300 s of a previous run will re-trigger the
incident-suppression effect above. The script header now says so.

`link_gap_records_total` moving 0 -> 34464 on a 2-frame gap injection is correct, not inflated: the dedup window is
65536, the injector jumps the sequence by 100000, and the metric counts sequences that *left* the window unreceived
(100000 - 65536). The 65535 still inside the window are reported separately as `link_missing_in_window`.

### Measured detection latency (run `verify-20260912T051348Z`, replay speed 4)

Two different quantities, both from stored timestamps:

- **Pipeline latency** (`receiver_to_alert_ms`): receiver ingest of the deciding evidence → alert written. This is the engineering figure.
- **Detection delay** (`onset_to_alert_observation_ms`): attack onset → alert, both in observation time. This is dominated by each detector's evidence requirement, not by the pipeline, and is the operationally meaningful figure.

| Scenario | Alert subtype | Pipeline ms | Detection delay | Why the delay is what it is |
|---|---|---|---|---|
| `syn_flood` | `syn_flood` | 544 | 0.1 s | Rate breach visible inside the first flow snapshot |
| `scan` | `horizontal_scan` | 625 | 3.0 s | Distinct-port threshold reached |
| `udp_amplification` | `udp_amplification_like` | 823 | 3.0 s | Response/request asymmetry over one window |
| `dga` | `dga_nxdomain_burst` | 571 | 4.5 s | NXDOMAIN burst threshold plus the ONNX model score |
| `dns_tunnel` | `dns_tunnel_like` | 575 | 15.0 s | Sustained query-volume/entropy evidence |
| `exfiltration` | `sustained_upload` | 599 | 40.1 s | EWMA baseline must establish, then be exceeded persistently |
| `encrypted` | `suspicious_tls_metadata` | 521 | 42.3 s | Several weighted metadata indicators must accumulate before abstention is lifted |
| `beaconing` | `periodic_beacon` | 586 | 210.6 s | Periodicity needs enough intervals for a stable MAD/median CV |

Pipeline latency: 8 samples, p50 **586 ms**, max **823 ms**. These are first-matching-alert values under light scenario load; sustained-load latency is a benchmark measurement and has not been taken yet.

Note on subtype refinement: the `syn_flood` episode's ground-truth label is `spoofed_source_like_syn_flood` and the alert's subtype is `syn_flood`, which is in the manifest's `expected_subtypes`. The detector refines a subtype only on evidence it can actually observe passively; it does not claim spoofing.

## Known limitations and risks to check first on the server

1. **PyFlink API surface.** `flink/sih_detect/job.py` uses the PyFlink 2.2 DataStream, Kafka connector, state, side-output and metric APIs as documented, but has not run. The first `docker compose up` shows any mismatch in `docker compose logs job-supervisor`.
2. **Flink 2.x configuration keys** (`execution.checkpointing.dir`, `state.backend.type`, …) follow the 2.x names. If one is ignored, checkpoints would not appear in MinIO: check the Flink UI's Checkpoints tab.
3. **PyFlink process mode** starts one Python worker per non-chained Python operator (about 10). The TaskManager memory limit (3 GiB) may need tuning after measuring.
4. **Zeek scripts** (`sensor/zeek/*.zeek`) have not yet been parsed by Zeek. The image build runs `zeek -a` and fails fast on syntax errors.
5. **UI:** TypeScript strict-mode typecheck runs in the `ui` build stage.
6. **Replay timing:** `SENDER_REPLAY_SPEED > 1` compresses wall-clock time only. Latency benchmarks must use speed 1 or synthetic open-loop runs.
7. **Registrable domains** come from a packaged suffix subset, not the full public suffix list (documented in `dga_features.py`).
8. **The DGA model is simulation-trained.** Its metrics measure separability of synthetic data only; confidence is `heuristic_score` and `simulation_only`.
9. **Sender loss while the receiver is down** is inherent (no return channel). It is visible as gaps and in the sender/receiver sequence comparison.
10. **Transitive Python dependencies** are frozen to `requirements.lock` at build time and exported by the bundle script; they are not committed as a lockfile.
