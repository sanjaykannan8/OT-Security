### The two failure-suite failures were test defects, not product defects

**`compose_restart`** — the recovery half passed (restored from `chk-254`, raw 14592->14592, alerts 212->212) and the post-fault
replay was delivered intact (sender sent 414/414, all 414 raw events stored). But it produced no alert, because the suite replayed
the *same* `scan` against the *same* entity `10.10.1.99` three times in four minutes: 05:36 opened the incident (`new`), 05:38
emitted an `updated` because accumulated evidence had grown, and 05:40 was suppressed. That is `incidents.py` behaving as
designed and documented: within an open incident (`incident_idle_ms` = 300 s) a repeat finding at the same severity and subtype
emits nothing unless the evidence grew past what was already reported, and increments `findings_suppressed`. The same `scan`
replayed at 05:47 passed, because by then 7 minutes of idle time had resolved the incident. Fix: each fault now replays a
different scenario (`scan`, `dga`, `udp_amplification`, `dns_tunnel`, `syn_flood`), so each post-fault check opens a genuinely
new incident. Suppressing a redundant third alert on a continuing incident is the wanted behaviour; only the assertion was wrong.

**`archive_lifecycle`** — the test stopped MinIO to simulate an archive outage, then ran the export cycle with
`docker compose run --rm archive-exporter`. Because that service declares `depends_on: minio-init`, Compose started its
dependencies and **restarted MinIO**, so the injected outage never existed: the cycle exported, verified and dropped normally and
0 rows remained instead of 1000. The functional half is nonetheless evidenced end to end - export, checksum verify, hot-partition
drop and restore of all 1000 aged rows, ending at status `deleted_hot`. Fix: `run --rm --no-deps`. Re-run needed for the
outage-tolerance half.

Neither failure indicates a defect in the system under test, but neither is counted as a pass here until the fixed suite re-runs.

### Measured detection latency (run `verify-20260912T051348Z`, replay speed 4)

Two different quantities, both from stored timestamps:

- **Pipeline latency** (`receiver_to_alert_ms`): receiver ingest of the deciding evidence → alert written. This is the engineering figure.
- **Detection delay** (`onset_to_alert_observation_ms`): attack onset → alert, both in observation time. This is dominated by each detector's evidence requirement, not by the pipeline, and is the operationally meaningful figure.

| Scenario | Alert subtype | Pipeline ms | Detection delay | Why the delay is what it is |
|---|---|---|---|---|
| `syn_flood` | `syn_flood` | 544 | 0.1 s | Rate breach visible inside the first flow snapshot |
| `scan` | `horizontal_scan` | 625 | 3.0 s | Distinct-port threshold reached |
| `udp_amplification` | `udp_amplification_like` | 823 | 3.0 s | Response/request asymmetry over one window |
| `dga` | `dga_nxdomain_burst` | 571 | 4.5 s | NXDOMAIN burst threshold plus the ONNX model score |
| `dns_tunnel` | `dns_tunnel_like` | 575 | 15.0 s | Sustained query-volume/entropy evidence |
| `exfiltration` | `sustained_upload` | 599 | 40.1 s | EWMA baseline must establish, then be exceeded persistently |
| `encrypted` | `suspicious_tls_metadata` | 521 | 42.3 s | Several weighted metadata indicators must accumulate before abstention is lifted |
| `beaconing` | `periodic_beacon` | 586 | 210.6 s | Periodicity needs enough intervals for a stable MAD/median CV |

Pipeline latency: 8 samples, p50 **586 ms**, max **823 ms**. These are first-matching-alert values under light scenario load; sustained-load latency is a benchmark measurement and has not been taken yet.

Note on subtype refinement: the `syn_flood` episode's ground-truth label is `spoofed_source_like_syn_flood` and the alert's subtype is `syn_flood`, which is in the manifest's `expected_subtypes`. The detector refines a subtype only on evidence it can actually observe passively; it does not claim spoofing.

## Known limitations and risks to check first on the server

1. **PyFlink API surface.** `flink/sih_detect/job.py` uses the PyFlink 2.2 DataStream, Kafka connector, state, side-output and metric APIs as documented, but has not run. The first `docker compose up` shows any mismatch in `docker compose logs job-supervisor`.
2. **Flink 2.x configuration keys** (`execution.checkpointing.dir`, `state.backend.type`, …) follow the 2.x names. If one is ignored, checkpoints would not appear in MinIO: check the Flink UI's Checkpoints tab.
3. **PyFlink process mode** starts one Python worker per non-chained Python operator (about 10). The TaskManager memory limit (3 GiB) may need tuning after measuring.
4. **Zeek scripts** (`sensor/zeek/*.zeek`) have not yet been parsed by Zeek. The image build runs `zeek -a` and fails fast on syntax errors.
5. **UI:** TypeScript strict-mode typecheck runs in the `ui` build stage.
6. **Replay timing:** `SENDER_REPLAY_SPEED > 1` compresses wall-clock time only. Latency benchmarks must use speed 1 or synthetic open-loop runs.
7. **Registrable domains** come from a packaged suffix subset, not the full public suffix list (documented in `dga_features.py`).
8. **The DGA model is simulation-trained.** Its metrics measure separability of synthetic data only; confidence is `heuristic_score` and `simulation_only`.
9. **Sender loss while the receiver is down** is inherent (no return channel). It is visible as gaps and in the sender/receiver sequence comparison.
10. **Transitive Python dependencies** are frozen to `requirements.lock` at build time and exported by the bundle script; they are not committed as a lockfile.
